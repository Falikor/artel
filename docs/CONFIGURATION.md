# Справочник конфигурации

[English](CONFIGURATION.en.md) · [Главная](../README.ru.md) · [Runbook](RUNBOOK.md) · [Жизненный цикл задачи](WORKFLOW.md)

Один JSON-файл в `config/` задаёт одного демона. Он может обслуживать один репозиторий или несколько `services[]`. Файл должен содержать JSON-объект: комментарии, завершающие запятые и shell-подстановки не поддерживаются. Полные шаблоны: [один репозиторий](../config/example.json.sample) и [несколько сервисов](../config/example-services.json.sample). В таблицах перечислены ключи JSON, значения по умолчанию и точные имена переменных окружения. Поля с `_` — внутреннее состояние, их не добавляют в конфиг.

## Приоритеты, типы и проверка

### Порядок источников

Для параметров с ENV-эквивалентом действует порядок:

1. Сохранённое решение в UI **Включить / Выключить**, если это один из поддерживаемых переключателей.
2. Переменная с префиксом проекта: например, `DEMO_BASE_BRANCH`.
3. Общая переменная: `BASE_BRANCH`.
4. Значение сервиса, если параметр разрешён в `services[]`.
5. Общий JSON-конфиг.
6. Значение по умолчанию.

В UI **По конфигу** убирает только ручное переопределение: ENV всё ещё главнее JSON. Префикс берётся из `jira.project` **в JSON**, сначала в исходном регистре, затем в верхнем. При проекте `demo` переменная `demo_BASE_BRANCH` имеет приоритет перед `DEMO_BASE_BRANCH`.

Пустые и состоящие из пробелов ENV не задают значение. `tmp/.env` заполняет только отсутствующие переменные: окружение запуска главнее файла, даже если уже существующая переменная пуста. Формат файла — по одной строке `KEY=VALUE`; поддерживаются комментарии отдельными строками с `#` и внешние кавычки вокруг значения. Это не shell-скрипт: `export`, `${VARIABLE}`, подстановка команд и комментарии после значения не обрабатываются. Секреты задавайте в ENV, не вставляйте строку `"$DEMO_JIRA_TOKEN"` в JSON — она останется буквальным текстом.

Исключения из общей схемы:

- `prompts` имеет отдельное UI-переопределение целого набора, без ENV и без настроек сервиса.
- `general.ci_id`, `general.enabled`, `general.service`, `general.role`, `general.office_group`, `general.character`, `services[]` и argv-команды тестов не имеют ENV-эквивалента.
- Имя, внешность и размещение, сохранённые в дашборде, главнее исходных значений отображения из конфига. Они не меняют технический идентификатор демона.
- Параметры сервиса накладываются только по [разрешённому списку](#сервисы-и-базовые-ветки), а не произвольным рекурсивным слиянием JSON.

### Идентификатор демона и область Jira

`jira.project` обязательно задаётся в JSON: он определяет идентификатор инстанса и ENV-префикс. `JIRA_PROJECT` меняет проект запросов Jira, но не переименовывает файлы памяти и логов и не меняет ENV-префикс.

`general.ci_id` задаётся только в JSON; при его наличии ключ инстанса — `ci<номер без ведущих нулей>`. Например, `CI000123` и `123` дают один ключ `ci123`; без КЭ проект `DEMO` даёт ключ `demo`. Имя JSON-файла и `general.name` на этот ключ не влияют. Два файла для одного проекта без КЭ будут обращаться к одним файлам состояния, памяти и управления. Разным демонам нужны разные ключи инстансов и отдельные рабочие клоны.

КЭ ограничивает поиск только вместе с `jira.ci_field`. Не придумывайте `ci_id` ради уникального имени: это реальный идентификатор из Jira. Общий проект также означает общий ENV-префикс: `DEMO_REPO_PATH` перекроет пути всех демонов этого проекта, даже с разными КЭ. Если им нужны разные пути, оставьте их в отдельных JSON; для разных секретов можно использовать отдельное окружение запуска/`ENV_FILE`.

### Типы, пустые значения и ограничения

Переключатели в JSON — `true`/`false`, интервалы и лимиты — числа, списки — массивы строк. В ENV переключатели принимают `true/false`, `1/0`, `yes/no`, `on/off`, `да/нет`; списки разделяются запятыми, включая `*_EXTRA_ARGS`: `--model,MODEL_ID`. Кавычки shell внутри списка не разбираются: `--model MODEL_ID` — один аргумент. Списки проходят очистку пробелов и удаление повторов без учёта регистра, поэтому не используйте повторяющиеся флаги с разными значениями.

`general.gigacode_chats_dir` — путь или JSON-массив путей; в ENV только один путь, без разделения запятыми. `memory.verify_commands` и `bitbucket.test_commands` — вложенные argv-массивы только в JSON. `general.enabled` учитывает именно JSON `false` и только при запуске через супервизор; прямой запуск файла демона этот флаг не использует.

У обычного resolver отсутствующий ключ и JSON `null` возвращают значение по умолчанию, а `""`, `[]` и `false` являются явными значениями. Дальнейшая обработка зависит от параметра:

| Значение | Что произойдёт |
|---|---|
| `explore.statuses: []` | Исследование выключено; нет списка статусов для возврата BLOCKED |
| `dependencies.ready_statuses: null` или отсутствует | Используются `jira.status_ready` |
| `dependencies.ready_statuses: []` | Готовность по имени статуса отключена; другие разрешённые признаки остаются |
| `general.temp_files: []` | Восстанавливается встроенный набор шаблонов |
| `services[].labels: []` или `keywords: []` | Включаются встроенные маркеры по имени сервиса; это не отключение маршрутизации |
| `memory.verify_commands: null` или отсутствует | Автоматический выбор тестовой команды |
| `memory.verify_commands: []` | Тесты для памяти не запускаются; структурные факты ещё можно подтвердить по коду |
| `bitbucket.test_commands: []` | Нет тестов, поэтому автоматическая публикация исправления PR запрещена |
| `prompts.profile: null`, `prompts.stages: null` | Ошибка проверки: нужны корректные типы и значения |

Некорректное число или переключатель часто заменяются значением по умолчанию, а не вызывают ошибку. Отрицательные интервалы не являются общим способом отключить функцию: используйте `enabled: false`. Нижние границы, где они есть, указаны в таблицах; для остальных интервалов задавайте положительные числа. Большинство разделов не отклоняют неизвестные ключи JSON: опечатка может остаться незамеченной. `prompts` проверяется строго, неизвестные поля и этапы отклоняются.

### Применение и проверка изменений

Переменные запуска, не поля JSON: `CONFIG_PATH` — конфиг одного демона (явный аргумент пути главнее), `ENV_FILE` — другой файл вместо `tmp/.env`, `DRY_RUN=true` — пробный запуск, `ARTEL_STOP_TIMEOUT` — ожидание остановки супервизором, по умолчанию 120 секунд. `ARTEL_RESTORE_ACTIVE` и `ARTEL_SUPERVISED` служебные — вручную их не задают.

Изменённый JSON и ENV применяются после перезапуска процесса. Переключатели UI и промпты перечитываются между задачами и фоновыми операциями; текущая работа продолжает использовать прежний снимок настроек. Переключатель не является немедленной остановкой уже работающего CLI.

Перед запуском выполните:

```bash
python3 jira_to_gigacode.py config/demo.json --check
python3 jira_to_gigacode.py config/demo.json --dry-run
```

`--check` проверяет конфиг, Git-клон и origin, доступность CLI и настроенных интеграций; он делает сетевые запросы, но не запускает выполнение задачи. `--dry-run` показывает один проход отбора без генерации, push, деплоя, переводов и комментариев. На Windows используйте `py -3` вместо `python3`.

Проверка не является полной JSON Schema: неверный необязательный параметр может проявиться только при выполнении соответствующей функции. Изменение области работы/промптов может остановить ранее сохранённый повтор до подтверждения в разделе **Повторы** — это предотвращает работу по задаче, взятой с прежним конфигом.

## Общие настройки

### Jira

| Ключ | По умолчанию | Назначение | Env |
|---|---|---|---|
| `jira.url` | не задан | URL Jira; обязателен при включённой Jira | `JIRA_URL` |
| `jira.token` | не задан | Bearer-токен Jira; обязателен при включённой Jira | `JIRA_TOKEN` |
| `jira.project` | не задан | Ключ проекта; обязательно задаётся в JSON даже при выключенной Jira | `JIRA_PROJECT` для запросов |
| `jira.status_analysis` | `[]` | Статусы задач на реализацию; обязательны при включённой Jira | `JIRA_STATUS_ANALYSIS` |
| `jira.status_ready` | `[]` | Целевые статусы после сдачи; обязательны при включённой Jira | `JIRA_STATUS_READY` |
| `jira.epic_name` | пустая строка | Название эпика для фильтра реализации; без пары полей фильтр не применяется | `JIRA_EPIC_NAME` |
| `jira.epic_link_field` | пустая строка | Поле связи с эпиком | `JIRA_EPIC_LINK_FIELD` |
| `jira.ci_field` | не задан | Числовой ID поля КЭ; используется с `general.ci_id` | `JIRA_CI_FIELD` |
| `jira.assignee` | не задан | Исполнитель для фильтра реализации; не ограничивает исследование | `JIRA_ASSIGNEE` |
| `jira.result_comments` | `true` | Отчёты и сообщения о решениях/блокировках в Jira | `JIRA_RESULT_COMMENTS` |

Поиск задач на выполнение всегда ограничен проектом и `status_analysis`. Пара `epic_name` + `epic_link_field`, пара `ci_id` + `ci_field` и `assignee` добавляют ограничения. Если задана только половина пары, соответствующий фильтр не действует. `status_ready` — названия целевых статусов, а не ID переходов; демон ищет доступный переход в один из них. Названия должны соответствовать workflow вашего проекта.

Исследование бэклога использует проект, КЭ и `explore.statuses`, **без фильтров эпика и исполнителя**. Это существенная разница: настройка `assignee` не ограничивает исследователя задачами этого пользователя. `jira.result_comments: false` отключает отчёты и часть уведомлений, но не является режимом только чтения и не запрещает выполнение задач, переходы или публикацию исследовательских предложений.

### Демон и репозиторий

| Ключ | По умолчанию | Назначение | Env |
|---|---|---|---|
| `general.enabled` | включён | Только JSON `false` исключает конфиг из запуска супервизором | — |
| `general.name` | не задан | Имя демона; имя из дашборда главнее | `DAEMON_NAME` |
| `general.ci_id` | не задан | Идентификатор КЭ; задаётся в JSON, определяет ключ инстанса | — |
| `general.repo_path` | текущая папка процесса | Рабочий клон одного репозитория; задайте явно или используйте `services[]` | `REPO_PATH` |
| `general.base_branch` | `develop` | Ветка origin для обычных задач и возврата клона | `BASE_BRANCH` |
| `general.base_branch_create_from` | `master` | База создания отсутствующей ветки из комментария Jira | `BASE_BRANCH_CREATE_FROM` |
| `general.branch_prefix` | `feature/ai_team` | Ветка задачи: `<prefix>/<KEY>` | `BRANCH_PREFIX` |
| `general.poll_interval_seconds` | `600` | Пауза между проходами поиска Jira, секунд | `POLL_INTERVAL` |
| `general.retry_cooldown_seconds` | `3600` | Пауза после двух неудач по задаче; BLOCKED не расходует технические ретраи | `RETRY_COOLDOWN_SECONDS` |
| `general.gigacode_path` | `gigacode` | Исполняемый файл CLI; должен быть доступен пользователю демона | `GIGACODE_PATH` |
| `general.gigacode_timeout_seconds` | `3600` | Таймаут основной генерации, секунд | `GIGACODE_TIMEOUT` |
| `general.require_success_marker` | `false` | Требовать последнюю строку `CODE_GENERATION_SUCCESS`; рекомендуется `true` | `REQUIRE_SUCCESS_MARKER` |
| `general.temp_files` | встроенный набор | Шаблоны исключаемых временных файлов: `.gigacode`, `.gigacode/*`, `tmp*.py`, `*_tmp.py`, `tmp_*.py`; непустой список заменяет набор, `[]` возвращает встроенный | `TEMP_FILES` |
| `general.compare_url` | не задан | Ссылка на diff в отчёте: `{branch}`, `{base}` без `origin/`, `{issue}` | `COMPARE_URL` |
| `general.service` | не задан | Имя одного сервиса для памяти и группировки; маршрутизация заменяет на `services[].name` | — |
| `general.role` | определяется по маркерам | `backend`, `frontend` или `other`; роль одного репозитория | — |
| `general.office_group` | значение `general.service` | Начальная группа офиса внутри проекта; ручное размещение в дашборде главнее | — |
| `general.character` | автоматический выбор | ID персонажа; выбор в дашборде главнее | — |
| `general.tokens_regex` | не задан | Regex расхода токенов в выводе CLI | `GIGACODE_TOKENS_REGEX` |
| `general.gigacode_chats_dir` | каталоги CLI в домашней папке | Путь или JSON-массив путей записей чатов; ENV принимает один путь | `GIGACODE_CHATS_DIR` |

`tokens_regex` должен содержать первую захватывающую группу с числом токенов; используется последнее совпадение. Например, в JSON `"tokens_regex": "total_tokens=(\\d+)"`. Это запасной источник статистики: сначала пользовательский regex, затем структурированный/текстовый вывод CLI и записи чатов. Пустой `gigacode_chats_dir` возвращает автоматический поиск в каталогах `.gigacode`, `.qwen`, `.gemini` домашней папки, по возможности с ограничением текущим репозиторием.

Используйте отдельный чистый рабочий клон для демона. `repo_path` — репозиторий продукта, над которым работает агент, а не папка установки Артели. Рекомендуются абсолютные пути: относительные зависят от рабочей папки запуска. `gigacode_path` содержит только имя/путь исполняемого файла, без аргументов командной строки. У основной генерации нет ключа `general.extra_args` или `general.model`: её модель задаётся настройками установленного CLI; для отдельных этапов предусмотрены собственные `extra_args`.

`general.require_success_marker: true` требует явного успешного маркера протокола. Значение по умолчанию `false` оставлено для совместимости, а не означает, что одного выхода CLI без ошибки всегда достаточно: проверяется результат работы в Git. BLOCKED — отдельный исход ожидания уточнений, а не техническая ошибка для кулдауна. Число технических неудач до паузы фиксировано в коде: 2; в JSON меняется длительность паузы.

## Переключатели

| Ключ | По умолчанию | Env |
|---|---|---|
| `jira.enabled` | `true` | `JIRA_ENABLED` |
| `jenkins.enabled` | `true` | `JENKINS_ENABLED` |
| `requirements.enabled` | `true` | `REQUIREMENTS_ENABLED` |
| `dependencies.enabled` | `true` | `DEPENDENCIES_ENABLED` |

У остальных функций ключ находится в своём разделе: `bitbucket.enabled`, `memory.enabled`,
`memory.auto_append`, `memory.auto_verify`, `review.enabled`, `explore.enabled`,
`explore.learn`, `retro.enabled`. Выбор UI хранится отдельно от JSON и применяется
на следующей безопасной границе работы. См. [переключатели в дашборде](DASHBOARD.md).

| Функция | Дополнительные условия |
|---|---|
| Исследование `explore.enabled` | Включена Jira, непустой `explore.statuses`, есть простой |
| Обучение в исследовании `explore.learn` | Включены исследование, `memory.enabled` и `memory.auto_append` |
| Проверка памяти `memory.auto_verify` | Включена память, есть кандидат и наступил интервал проверки |
| Ретроспектива `retro.enabled` | В обычном цикле включена Jira, есть сданные задачи, наступили окно и интервал |
| Ручная переделка `requirements.enabled` | Включена Jira и есть запрос в очереди переделок |
| Зависимости `dependencies.enabled` | Проверяются при отборе задач Jira; не запускают задачу вне её области поиска |
| Bitbucket `bitbucket.enabled` | Полная настройка Server/Data Center и история сданных Артелью задач; может работать при выключенной Jira |

Выключение Jira не останавливает процесс: обработка PR и проверка памяти могут продолжаться. Выключение памяти прекращает чтение и сбор уроков, но не удаляет сохранённые записи. `memory.auto_append: false` запрещает новые кандидаты, при этом прежние подтверждённые записи читаются, а существующие кандидаты могут проверяться. У всех сервисов демона одно UI-переопределение переключателя; разное поведение сервисов задавайте в JSON с режимом **По конфигу**.

Фоновая работа выполняется, когда нет доступных задач: PR → ретроспектива → исследование → проверка памяти. Интервалы не создают отдельные параллельные таймеры: длинная задача или предыдущий этап могут отложить следующий запуск.

## dependencies

| Ключ | По умолчанию | Env |
|---|---|---|
| `dependencies.enabled` | `true`; также переключатель в панели демона | `DEPENDENCIES_ENABLED` |

Для фронтенда своего КЭ каждый связанный бэкенд должен быть в `ready_statuses` либо, при `allow_code_branch: true`, иметь подтверждённую ветку с изменениями из панели Jira **Development / Разработка**. Категория Done учитывается только с `accept_done: true`; наличие пустой ветки не считается готовностью. Если у бэкенда уже запрошена переделка постановки, старый готовый статус/ветка не снимают ожидание.

Для бэкенда другого или неподтверждённого КЭ требуется точный `external_ready_label` **на фронтенд-задаче**. По умолчанию это `backend-ready`. Лейбл не отменяет ожидание бэкенда своего КЭ. Без пары `ci_id` + `ci_field` принадлежность своему КЭ не подтверждается, даже если обе задачи в одном проекте.

`link_types` фильтрует по имени типа связи Jira, например `Blocks`, а не по фразе направления `is blocked by`; рассматриваются обе стороны выбранных связей. `role: other` явно исключает сервис из классификации backend/frontend; неизвестная или неоднозначная роль может потребовать уточнения. У ролей зависимости свой набор маркеров; маркеры маршрутизации `services[].labels/keywords` также помогают сопоставить сервис и его явную роль.

Путь `memory/{key}.md` — базовое имя семейства файлов. Структурированные записи хранятся рядом в `.store.json`, постоянные правила — в `.rules.md`, аудит — в `.history.jsonl` и одном ротированном `.history.jsonl.1`: например, `memory/demo.md.store.json`. Старый `.md` сохраняется. Относительный `memory.path` считается от папки установки Артели; `~` раскрывается. Сохраняйте `{key}` в общем шаблоне, иначе разные сервисы будут писать в одну память.

В промпт попадают правила и подходящие подтверждённые знания в пределах `max_chars`; кандидаты не становятся истиной только от частого повторения или успешной задачи. По истечении `review_after_days` подтверждённая запись возвращается на проверку. Лимиты кандидатов/подтверждённых/возраста/интервалов и бюджет символов имеют минимум 1; `history_max_bytes` — минимум 16384. Установка лимита в 0 не выключает память.

Автопроверка сопоставляет цитаты с кодом, запускает выбранные тесты отдельным процессом и получает независимое заключение. Проверяемая ветка должна быть доступна в Git. Спорные записи остаются для человека; техническая ошибка откладывает проверку на `verify_retry_hours`. `verify_timeout` и `verify_test_timeout` имеют минимум 1 секунду. При `verify_commands: []` возможно подтверждение только структурного факта по коду, без утверждения о проверенном поведении. Подробнее — [команды тестов](#команды-тестов).

Без списка задача остаётся в текущем статусе, но всё равно ожидает изменения постановки, не расходуя технические ретраи.

## Промпты и специализация демона

Раздел `prompts` задаётся на верхнем уровне JSON и действует для всех сервисов демона.
Сохранённые настройки вкладки **Промпты** главнее JSON. **Из конфига → Сохранить** убирает
UI-переопределение. ENV-эквивалентов у этих настроек нет.

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `prompts.profile` | `developer` | `developer`, `testing` или `custom`; тестировщик составляет сценарии и добавляет/запускает автотесты |
| `prompts.subagent` | `jira-to-deploy-orchestrator` | Имя установленного субагента для выполнения и доработки: 1–80 латинских букв, цифр, `_` и `-`, начинается с буквы, без `/` |
| `prompts.instructions` | пустая строка | Общие дополнительные инструкции для всех этапов, до 6000 символов |
| `prompts.stages.generation` | пустая строка | Выполнение задачи и ручная переделка |
| `prompts.stages.review` | пустая строка | Независимое ревью |
| `prompts.stages.rework` | пустая строка | Доработка после ревью |
| `prompts.stages.explore` | пустая строка | Исследование бэклога |
| `prompts.stages.pr_review` | пустая строка | Замечания Bitbucket и ответы |
| `prompts.stages.retro` | пустая строка | Ретроспектива |
| `prompts.stages.memory` | пустая строка | Проверка кандидатов памяти |

У каждого поля этапа собственный лимит 6000 символов. Это текст, дополняющий запрос
GigaCode, а не shell-команда и не замена обязательного протокола Артели. Настройки UI
хранятся в `logs/{instance}-prompts.json`; применяются между задачами и фоновыми операциями.
Изменение поведения требует подтверждения старого повтора. [Примеры и порядок работы](PROMPTS.md).

## Сервисы и базовые ветки

У сервисов не произвольные JSON-overrides. Поддерживаются поля ниже; остальные разделы действуют для всего демона. Подробные примеры и маршрутизация — [в жизненном цикле задачи](WORKFLOW.md).

| Настройка | У сервиса задана | У сервиса не задана |
|---|---|---|
| `name`, `repo_path` | обязательны; имя сервиса и путь его клона | запись без них игнорируется |
| `labels`, `keywords` | массивы маркеров маршрутизации | встроенные слова по имени сервиса |
| `role` | роль задачи сервиса: `backend`, `frontend` или `other` | определяется по имени сервиса, лейблам и словам в названии задачи |
| `base_branch`, `base_branch_create_from`, `branch_prefix`, `compare_url` | заменяет общую из `general` | берётся общая |
| `jenkins`, `review`, `memory`, `bitbucket` | **сливается** с общим разделом: ключи сервиса главнее, остальные — из общего | берётся общий раздел целиком |

Обычно в общий `jenkins` кладут `url` и `user` (токен — в `tmp/.env`), а у сервиса — только свой
`job_name`. **Переменные окружения главнее и общих настроек, и настроек сервиса:** `REPO_PATH`,
`JENKINS_JOB`, `COMPARE_URL`, `BRANCH_PREFIX`, `BASE_BRANCH`, `BASE_BRANCH_CREATE_FROM` (в том числе с префиксом проекта, `DEMO_JENKINS_JOB`)
при сервисах дали бы всем одно значение — проверка окружения при старте предупредит, если такая
переменная перекрывает настройку сервиса.

Сервис задачи демон определяет по **лейблам** (точное совпадение, без учёта регистра) и **словам в
названии** (целые слова: «[Бек] Добавить поле», «WEB: кнопка»; «webhook» — не «web»):

- подошёл ровно один сервис — задача делается в его репозитории, с его джобой Jenkins;
- не подошёл ни один или подошли несколько — демон задачу **не берёт** и один раз пишет в неё
  комментарий: какие лейблы и слова он понимает, или просьбу разбить задачу на несколько. Как только
  название или лейблы поменяются, задача проверяется снова и, если сервис стал понятен, берётся в работу.

Другие разделы внутри `services[]` не накладываются на общие настройки: поддерживаются только поля из таблицы.

Слияние разделов неглубокое: массив `review.extra_args` сервиса полностью заменяет общий массив. `branch_prefix` и `compare_url` переопределяются только непустым значением; пустая строка не очищает общий параметр. `base_branch` и `base_branch_create_from` накладываются при наличии ключа: `null` затем приводит к встроенному значению resolver, а пустая строка — к ошибке проверки Git ref. Для наследования ветки лучше просто не задавать ключ.

Пустые `labels`/`keywords` возвращают встроенные маркеры для имён `back`, `web`, `front`, `mobile`; для другого имени маркером становится само имя. Лейбл не имеет приоритета над названием: если лейбл указывает на бэкенд, а слово в названии на фронтенд, совпадут два сервиса и задача будет пропущена. Имена сервисов должны быть уникальными и стабильными, поскольку входят в имена файлов памяти. Записи без `name` или `repo_path` игнорируются; если допустимых записей не осталось, включится режим одного репозитория из `general.repo_path`.

Память сервисов разделяется автоматически: `memory/{инстанс}-{сервис}.md`. Вложенные настройки `jira`, `explore`, `retro`, `dependencies`, `requirements`, `prompts` внутри `services[]` не поддерживаются.

## Дополнительные правила

### Какие ветки используются

| Параметр | Для чего нужен | Формат |
|---|---|---|
| `general.base_branch` | База обычной задачи и ветка возврата рабочего клона после доставки | Имя ветки, например `main`; `origin/main` и `refs/heads/main` нормализуются |
| `general.base_branch_create_from` | Основа для создания ещё отсутствующей базовой ветки, указанной пользователем в Jira | Имя ветки, по умолчанию `master` |
| `general.branch_prefix` | Имя рабочей ветки задачи `<prefix>/<KEY>` | Например `feature/ai_team` → `feature/ai_team/DEMO-42` |
| `explore.base` | Ревизия временной копии исследователя | Git ref, обычно `origin/main` |
| `memory.verify_base` | Ревизия, на которой проверяется кандидат памяти | Git ref, обычно `origin/main` |

Явный пользовательский маркер `branch:` / `ветка:` в Jira меняет базу конкретной задачи. Он не переименовывает общую ветку возврата и не меняет автоматически базу исследователя или памяти. Для репозитория с единственной основной веткой `main` задайте **обе** общие ветки `main`. Если `explore.base`/`memory.verify_base` не заданы, их `origin/<base_branch>` определяется после наложения настроек сервиса.

После доставки демон пытается выполнить `git checkout <base_branch>` и `git pull --ff-only origin <base_branch>`. Ошибка checkout или невозможность fast-forward логируется; принудительного сброса этой ветки данный шаг не делает. Поэтому настройка `base_branch: "master"` означает намерение вернуться и обновить `master`, но не гарантирует успешное обновление при конфликте или недоступной сети. [Жизненный цикл ветки](WORKFLOW.md#базовая-ветка).

### Команды тестов

`memory.verify_commands` и `bitbucket.test_commands` — массивы argv-массивов, например `[["python3", "-m", "pytest", "-q"], ["npm", "run", "test:unit"]]`. Первый элемент — исполняемый файл, остальные — его отдельные аргументы. Строка `"pytest && npm test"` не является допустимой записью. Shell-подстановки, `&&`, `|` и перенаправления автоматически не интерпретируются.

Список проверяется на непустые argv-массивы и строки; учитываются только первые **5 команд**. Команды выполняются последовательно во временном Git worktree, от его корня, с правами пользователя демона. Worktree изолирует файлы, но не создаёт контейнер или отдельную сетевую среду. Пути к локальным скриптам должны существовать в этой копии, а зависимости тестов — быть доступны. Не рассчитывайте на установленный только в основном клоне `node_modules` или локальное виртуальное окружение, если команда не умеет их находить.

При отсутствующем ключе или `null` выбирается **первый подходящий** стек:

| Признак репозитория | Автоматическая команда |
|---|---|
| `pom.xml` | Maven wrapper, если есть, иначе `mvn -B test` |
| `build.gradle` / `build.gradle.kts` | Gradle wrapper, если есть, иначе `gradle test --no-daemon` |
| `package.json` с `scripts.test` | `pnpm test` при `pnpm-lock.yaml`, иначе `yarn test` при `yarn.lock`, иначе `npm test` |
| `go.mod` | `go test ./...` |
| `Cargo.toml` | `cargo test` |
| Папка `tests` и настройки pytest | Текущий Python: `-B -m pytest -q` |
| Папка `tests` без признаков pytest | Текущий Python: `-B -m unittest discover -s tests` |
| Ничего из перечисленного | Пустой список |

Признаки pytest: `pytest.ini`, `conftest.py` в корне или `[tool.pytest` в `pyproject.toml`. Для Windows автоматически выбираются `.cmd`/`.bat` варианты Maven, Gradle и Node-менеджеров. Явные команды не преобразуются под другую ОС: указывайте `npm.cmd` и корректный Python-путь самостоятельно. Для монорепозитория или нестандартной структуры задавайте команды явно.

Проверяющий памяти выбирает релевантные команды из разрешённого списка; исправление PR запускает все выбранные конфигом команды. Пустой список не даёт автоматический push в PR, а в памяти допускает только структурное доказательство по коду. Это разные этапы: явный `memory.verify_commands` не перенастраивает тесты Bitbucket.

### TLS и доступы

Jira и Bitbucket работают через Python REST-клиенты, без MCP. Настройки GigaCode MCP не задают доступ этим клиентам. Git использует собственные credentials/SSH/HTTPS-настройки пользователя, а не автоматически токен Bitbucket из JSON.

| Интеграция | Проверка сертификата в текущей реализации |
|---|---|
| Jira | Сертификат и имя хоста не проверяются; ключей `jira.verify_ssl` и `jira.ca_file` нет |
| Jenkins | Сертификат и имя хоста не проверяются; аналогичных JSON-переключателей нет |
| Bitbucket, настройки TLS отсутствуют | HTTPS, но без проверки сертификата и имени хоста |
| Bitbucket, `verify_ssl: true` | Проверка доверенной цепочки и имени хоста; без `ca_file` — доверенные CA Python/ОС |
| Bitbucket, задан `ca_file`, `verify_ssl` отсутствует | Проверка включена с указанным PEM |
| Bitbucket, `verify_ssl: false` и задан `ca_file` | Явное `false` главнее: CA-файл не включает проверку |

Отсутствие CA-файла не означает отсутствие шифрования HTTPS, но при выключенной проверке не подтверждается подлинность сервера. Для Bitbucket с общедоверенным сертификатом достаточно `"verify_ssl": true`, без сертификата в конфиге. Для своего CA укажите абсолютный путь к PEM. ENV `BITBUCKET_VERIFY_SSL` также имеет приоритет над JSON и над автоматическим включением по `ca_file`.

### Параметры, которые задаются вне JSON

Jenkins запускается только по лейблу `jenkins_{стенд}[_migration]`. Имена параметров `refName`, `filter`, `MIGRATION` и встроенное соответствие стендов заданы в `jira_gigacode/jenkins.py`; отдельными ключами JSON они не настраиваются.

У `requirements` единственный пользовательский ключ — `enabled`. Причина и задача переделки задаются в дашборде. Отдельных ключей `retry.max_attempts`, `general.model`, `jira.jql`, `dashboard.port`, `prompts.shell_script` в конфиге демона нет. При необходимости выбирать другую модель основного CLI используйте настройки самого CLI, а при выборе ветки/задачи — поддерживаемые поля и действия дашборда.

## Готовые варианты конфигурации

Два первых примера с Jira-полями — самостоятельные JSON-конфиги после замены адресов, путей и статусов. Токены для них задаются отдельно в ENV. Остальные блоки помечены как **фрагменты**: перенесите их ключи в существующий конфиг, сохранив обязательные поля. Это инструкции редактирования, не отдельный механизм импорта/наследования файлов.

### Один репозиторий, основная ветка main

Самостоятельный `config/demo.json`: разработка по выделенному статусу `Ready for AI`, возврат BLOCKED в `TO DO`, обязательное ревью, без Jenkins и Bitbucket.

```json
{
  "jira": {
    "url": "https://jira.example.com",
    "project": "DEMO",
    "status_analysis": ["Ready for AI"],
    "status_ready": ["Code Review"],
    "result_comments": true
  },
  "general": {
    "name": "Demo developer",
    "repo_path": "/srv/repos/demo",
    "base_branch": "main",
    "base_branch_create_from": "main",
    "role": "backend",
    "poll_interval_seconds": 600,
    "require_success_marker": true
  },
  "review": {
    "enabled": true,
    "block_on_changes": true,
    "on_no_verdict": "block",
    "max_rework_rounds": 1
  },
  "explore": {
    "enabled": true,
    "statuses": ["TO DO"],
    "learn": false
  },
  "jenkins": {"enabled": false},
  "bitbucket": {"enabled": false}
}
```

В `tmp/.env` отдельно добавьте `DEMO_JIRA_TOKEN=<ваш токен>`. Здесь `<ваш токен>` — заполнитель, не значение для копирования. Установите используемого субагента в GigaCode CLI, убедитесь в наличии `origin/main`, замените названия статусов на ваши и выполните `--check`, затем `--dry-run`.

Этот вариант не ограничивает задачи эпиком/исполнителем. Чтобы сузить реализацию, добавьте `jira.assignee` или оба поля эпика. Исследование всё равно охватит `TO DO` всего проекта; при необходимости ограничьте его настоящим КЭ через пару `ci_id` + `ci_field`.

### Backend и frontend в одном КЭ

Самостоятельный конфиг одного демона с двумя клонами. `CI12345` и `ci_field: "12345"` — **разные сущности**: значение объекта КЭ и ID поля Jira. В примере номера совпадают только для удобства; замените каждый на свой. Бэкенд работает от `develop`, фронтенд — от `main`.

```json
{
  "jira": {
    "url": "https://jira.example.com",
    "project": "DEMO",
    "ci_field": "12345",
    "status_analysis": ["Ready for AI"],
    "status_ready": ["Code Review"]
  },
  "general": {
    "name": "Demo team",
    "ci_id": "CI12345",
    "base_branch": "develop",
    "base_branch_create_from": "main",
    "require_success_marker": true
  },
  "services": [
    {
      "name": "back",
      "role": "backend",
      "repo_path": "/srv/repos/demo-back",
      "labels": ["backend"],
      "keywords": ["backend", "бек", "бэк"],
      "memory": {"verify_commands": [["./mvnw", "-B", "test"]]}
    },
    {
      "name": "web",
      "role": "frontend",
      "repo_path": "/srv/repos/demo-web",
      "base_branch": "main",
      "base_branch_create_from": "main",
      "labels": ["frontend"],
      "keywords": ["frontend", "фронт"],
      "memory": {"verify_commands": [["npm", "run", "test:unit"]]}
    }
  ],
  "dependencies": {
    "enabled": true,
    "external_ready_label": "backend-ready",
    "allow_code_branch": true,
    "accept_done": false
  },
  "review": {
    "enabled": true,
    "block_on_changes": true,
    "on_no_verdict": "block"
  },
  "explore": {"statuses": ["TO DO"]},
  "jenkins": {"enabled": false}
}
```

Токен — `DEMO_JIRA_TOKEN`. Не задавайте `REPO_PATH`/`DEMO_REPO_PATH` или `BASE_BRANCH`/`DEMO_BASE_BRANCH` в общем окружении: они отменят различия сервисов. Пример предполагает Maven wrapper у бэкенда и `test:unit` у фронтенда; замените команды на существующие тесты проектов.

Задача с лейблом `backend` попадёт в первый клон, `frontend` — во второй. Если связанный backend этого же КЭ ещё не готов, frontend ждёт. Бэкенд другого КЭ требует `backend-ready` на frontend-задаче. Без подходящего маркера или при совпадении обоих сервисов реализация не начинается.

### Демон-тестировщик

**Фрагмент для первого конфига**: меняет роль и инструкции, сохраняя доставку результата, проверку ветки и маркеры завершения.

```json
{
  "prompts": {
    "profile": "testing",
    "subagent": "jira-to-deploy-orchestrator",
    "instructions": "Проверяй критерии приёмки и регрессии. Используй существующий тестовый стек проекта.",
    "stages": {
      "generation": "Добавь воспроизводимые тесты. Не меняй продуктовый код без прямого требования задачи.",
      "review": "Проверь, что тесты выявляют исходный дефект и не ослабляют существующие проверки.",
      "pr_review": "Для каждого замечания приведи результат проверки или воспроизводимое обоснование возражения."
    }
  },
  "memory": {
    "enabled": true,
    "auto_append": true,
    "auto_verify": true,
    "verify_commands": [["python3", "-m", "pytest", "-q"]]
  }
}
```

`testing` не устанавливает тестовый framework и не добавляет CLI-субагента автоматически. Имя `subagent` должно соответствовать установленному определению; без своего тестового субагента можно оставить стандартный оркестратор и профиль `testing`. Эти же настройки доступны во вкладке **Промпты**. `profile: "custom"` убирает встроенную специализацию тестировщика и оставляет ваши инструкции.

Если это второй демон, а не смена роли первого, создайте ему отдельный клон, реальную непересекающуюся область Jira и уникальный ключ инстанса. Копирование `demo.json` в `tester.json` само по себе не даёт новую идентичность и не предотвращает выбор одной задачи двумя демонами.

### Сопровождение PR без новых задач Jira

**Фрагмент для уже работающего демона** с историей сданных задач. Сохраняйте прежние `jira.project`, `ci_id`, `repo_path` и файлы доставок: по ним находятся его PR.

```json
{
  "jira": {"enabled": false},
  "bitbucket": {
    "enabled": true,
    "url": "https://bitbucket.example.com",
    "project": "DEMO",
    "repo": "demo",
    "bot_user": "artel-bot",
    "verify_ssl": true,
    "batch_comments": true,
    "max_per_cycle": 1,
    "max_tasks_per_cycle": 20,
    "poll_interval_seconds": 600,
    "test_commands": [["python3", "-m", "pytest", "-q"]]
  },
  "memory": {"auto_verify": false}
}
```

Задайте `DEMO_BITBUCKET_TOKEN` в окружении. `verify_ssl: true` использует доверенные CA без указания сертификата; для вашего CA добавьте `ca_file`. Git должен отдельно уметь читать и пушить ветку. Выключенная Jira прекращает обычный отбор задач, переделки, исследование и плановую ретроспективу; PR продолжают обрабатываться. Это режим исправления и ответов, **не только чтения**. Для остановки PR выключите `bitbucket.enabled`.

### Меньше фоновой активности, память только читается

**Фрагмент для существующего конфига**: выполнение задач остаётся включённым; нет новых уроков, исследований, ретроспектив и автоматических PR-исправлений. Подтверждённая память всё ещё используется. `TO DO` оставлен как статус ожидания BLOCKED.

```json
{
  "memory": {
    "enabled": true,
    "auto_append": false,
    "auto_verify": false
  },
  "explore": {
    "enabled": false,
    "statuses": ["TO DO"],
    "learn": false
  },
  "retro": {"enabled": false},
  "bitbucket": {"enabled": false}
}
```

Для полностью пробного прохода используйте `--dry-run`: универсального JSON-ключа `read_only` нет. Для отключения всего процесса из набора супервизора предусмотрен `general.enabled: false`; это не эквивалент выключению отдельных интеграций.

### Windows и разные модели для этапов

**Фрагмент для первого конфига**. Прямые слеши допустимы в путях Windows; при обратных используйте двойные `\\` в JSON. Путь с пробелами остаётся одним элементом argv и не требует дополнительных shell-кавычек внутри строки.

```json
{
  "general": {
    "repo_path": "C:/Work/demo",
    "gigacode_path": "C:/Users/Operator/AppData/Roaming/npm/gigacode.cmd",
    "base_branch": "main",
    "base_branch_create_from": "main"
  },
  "review": {
    "extra_args": ["--model", "YOUR_REVIEW_MODEL"],
    "timeout_seconds": 1800,
    "on_no_verdict": "block"
  },
  "explore": {
    "extra_args": ["--model", "YOUR_EXPLORATION_MODEL"],
    "timeout_seconds": 900
  },
  "retro": {
    "extra_args": ["--model", "YOUR_RETROSPECTIVE_MODEL"]
  },
  "memory": {
    "verify_commands": [["C:/Python311/python.exe", "-m", "pytest", "-q"]],
    "verify_extra_args": ["--model", "YOUR_VERIFICATION_MODEL"]
  },
  "bitbucket": {
    "test_commands": [["npm.cmd", "run", "test:unit"]],
    "extra_args": ["--model", "YOUR_PR_MODEL"]
  }
}
```

`YOUR_..._MODEL` — заполнители: замените их ID моделей, доступных в вашей установленной версии GigaCode CLI. Если у всех этапов одна модель, удалите `extra_args` и используйте настройки CLI. Конкретные пути Python/GigaCode также заменяются. `general.gigacode_path` не должен содержать `--model`; ключа `general.extra_args` нет. Запуск проверки на Windows: `py -3 jira_to_gigacode.py config/demo.json --check`.

### Почему заданное значение не применяется

| Симптом | Что проверить |
|---|---|
| Исправили JSON, поведение прежнее | Перезапущен ли процесс; нет ли UI-переопределения или ENV выше по приоритету |
| Все сервисы работают с одной веткой/папкой | Общие и проектные `BASE_BRANCH`, `REPO_PATH`, `BRANCH_PREFIX` |
| Смена имени не создала второго демона | `general.name` — отображение; идентичность задаётся проектом/КЭ |
| Выключили сбор уроков, проверка всё ещё работает | `auto_append` и `auto_verify` — независимые функции |
| Интервал исследования меньше 14 дней не срабатывает | Нижняя граница `min_hours_between` всегда 336 часов |
| Frontend ждёт, хотя backend Done | По умолчанию `accept_done: false`; задайте готовые статусы или включите категорию Done |
| Поставили `backend-ready`, а свой backend всё ещё блокирует | Лейбл разрешает внешний КЭ, не заменяет готовность своего |
| Новые настройки модели не влияют на генерацию | `review.extra_args` действует только на ревью; основная модель берётся из CLI |
| PR исправлен локально, но не опубликован | Есть ли непустые тестовые команды, прошли ли проверки и не изменился ли PR |
| Порт дашборда не меняется из JSON | HTTP-параметры задаются CLI дашборда/супервизора, не конфигом демона |

## Дашборд и обновление

Параметры HTTP-сервера (`--host`, `--port`, `--logs`, `--assets`, `--no-control` и пути файлов) задаются аргументами запуска: [справочник дашборда](DASHBOARD.md). У updater свой CLI: [обновление и резервные копии](../UPDATE.md). Они не являются полями JSON-конфига демона.
