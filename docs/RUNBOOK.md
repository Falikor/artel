# Runbook: когда нужна помощь

[Главная](../README.md) · [Конфигурация](CONFIGURATION.md) · [Процессы и логи](OPERATIONS.md)

Команды выполняются из папки Артели. На Windows заменяйте `python3` на `py -3 -X utf8`.
`team` в `restart` — имя файла `config/team.json`; `ID` в `retry`/`pr` — идентификатор
инстанса из `logs/` (например `ci42` или `team`), а не отображаемое имя персонажа.

## Задача зависла

1. Откройте демона → **Логи GigaCode** и **Лог демона**. Посмотрите последний инструмент,
   ошибку и время последнего события. Отсутствие новых строк само по себе не доказывает зависание:
   инструмент может выполнять длинную команду.
2. Выполните `python3 artel.py status`. Если демон работает, сравните длительность с
   таймаутом текущего этапа: `general.gigacode_timeout_seconds`, `review.timeout_seconds`,
   `bitbucket.timeout_seconds` или `memory.verify_timeout`.
3. Если нужен ответ на вопрос, смотрите комментарий Jira и состояния ожидания ниже.
   Не повышайте лимит ретраев для задачи, которой не хватает постановки.
4. Для прерывания нажмите **Остановить** в настройках демона. Это прерывает CLI; после
   проверки результата запустите демона и разрешите повтор в **Повторах**, если он требуется.
   Остановка всего сервиса: `python3 artel.py down`.

Прерванные коммиты сохраняются механизмом восстановления в `refs/ai-team-interrupted/…`.
Не удаляйте журнал ретраев и Git refs, чтобы «разблокировать» задачу. Если код уже опубликован,
сначала проверьте ветку и PR: для незавершённого перевода Jira повторная генерация не нужна.

## Демон не берёт задачу

Проверяйте условия по порядку; кнопка повторного опроса не обходит их.

1. **Процесс и конфиг.** `python3 artel.py status`, затем
   `python3 jira_to_gigacode.py config/team.json --check`. Файл должен иметь расширение `.json`,
   `general.enabled` не должен быть `false`. В панели Jira должна быть включена.
2. **Область поиска.** Проверьте проект, статус из `jira.status_analysis`, эпик, КЭ и исполнителя.
   `jira.assignee` ограничивает обычные задачи, но не исследование бэклога.
   Увидеть выбор без реализации: `python3 jira_to_gigacode.py config/team.json --dry-run`.
3. **Маршрутизация.** Для `services[]` название и лейблы должны однозначно выбрать один сервис.
   Если подходит ноль или несколько сервисов, исправьте маркеры; демон пишет причину в Jira.
4. **Зависимости.** Фронтенд своего КЭ ждёт готового статуса бэкенда либо подтверждённой ветки
   с кодом в Development. Для бэкенда другого КЭ нужен согласованный лейбл `backend-ready`
   на фронтенд-задаче. [Подробные условия](WORKFLOW.md).
5. **Повторы.** Откройте **Повторы**: задача может быть исключена, на паузе, в кулдауне или
   ждать подтверждения после прерывания/изменения конфига.
6. **Рабочий клон.** Проверьте причину в логе: грязная рабочая копия, недоступная ветка origin,
   Git-доступ или CLI блокируют выполнение. Сохраните собственные изменения обычным способом.

После исправления конфига выполните `python3 artel.py restart team`, затем в панели
**Настройки → Проверить Jira сейчас**. Для исследования бэклога отдельно нужны
`explore.enabled` и непустые `explore.statuses`.

## Как снять паузу или подтвердить повтор

В панели демона → **Повторы** выберите задачу и разрешите повтор. CLI-эквивалент:

```bash
python3 artel.py retry list ID
python3 artel.py retry resume ID TEAM-123
```

`resume` снимает исключение/паузу и кулдаун этой задачи и разрешает следующую попытку.
Текущий JQL, маршрутизация и зависимости продолжают действовать. Это не команда запуска
любой задачи по ключу. Для новой постановки выполненной задачи используйте **Переделки**.

Если остановлен сам демон, сначала нажмите **Запустить** или выполните
`python3 artel.py restart team`. **Пауза сцены** останавливает только анимацию и не влияет
на выполнение. Выключенная функция включается в **Настройки → Функции демона**;
**По конфигу** возвращает управление JSON и ENV. Новый выбор применяется на безопасной границе,
а не посреди текущей задачи.

## BLOCKED: нужен ответ на вопрос

`CODE_GENERATION_BLOCKED` — отдельный исход ожидания, а не техническая ошибка с ретраями.
Демон публикует вопрос субагента в Jira и пробует вернуть задачу в один из `explore.statuses`
прямым доступным переходом. Если перехода нет, задача остаётся в ожидании с объяснением:
исправьте статус вручную или настройку, не удаляя состояние демона.

Ответьте в Jira или уточните заголовок/описание. Демон возвращается после изменения постановки
или комментариев человека; свои сообщения и простая смена статуса повтор не запускают.
Для этого ожидания нет интервала в 14 дней. Текущая область проекта, КЭ, исполнителя,
маршрутизация, зависимости и ручные запреты всё равно проверяются.
Для ручной переделки сохраняется её отдельная очередь и аналитика.

## Bitbucket: спорное замечание или `sending`

`sending` означает, что результат POST неизвестен: ответ мог появиться на сервере.
Откройте PR и проверьте обсуждение перед любым действием. Не создавайте ответ повторно вручную,
пока не убедитесь, что первого нет.

```bash
python3 artel.py pr list ID
python3 artel.py pr retry ID RECORD_ID
python3 artel.py pr skip ID RECORD_ID
```

`RECORD_ID` — полный ID записи из `list`. `retry` сначала сверяет подготовленную отправку
с сервером, `skip` завершает обработку этой версии обсуждения без сообщения.
Для спорного замечания `retry` разрешает повторную оценку. [Подробный порядок](BITBUCKET.md).

## Решение владельца видно в Jira

Запрос подтверждения повтора, спорное замечание PR и неопределённая отправка `sending`
публикуются в задаче Jira с причиной, ссылкой на PR/обсуждение и следующим действием.
Повторное состояние обновляет собственный комментарий вместо создания дублей.
Новый ответ в Jira сам по себе не разрешает рискованный повтор: используйте панель или
указанную CLI-команду. Для BLOCKED ответ служит уточнением постановки, как описано выше.

Сообщения включены вместе с `jira.enabled` и `jira.result_comments`. При отключении Jira
или комментариев смотрите панель и CLI. Очередь уведомлений сохраняется в
`logs/{ID}-notifications.json`. Ошибка чтения или редактирования Jira не теряет решение;
после неопределённого POST демон сначала ищет свой ответ и не повторяет отправку вслепую.

## После обновления старый интерфейс или нет демонов

1. Откройте HTTP-адрес живого дашборда, а не `output/Artel_Interactive.html` — это презентация.
2. Проверьте пакет командой updater `--verify-only` с правильным `--target`, затем обновите
   страницу. Путь `--assets`/`OFFICE_ASSETS` может указывать на старые внешние спрайты.
3. Сверьте версии через `python3 artel.py status`; перезапуск устаревших демонов:
   `python3 artel.py restart --outdated`.
4. Если карточек нет, проверьте, что `--logs` указывает на журнал действующих демонов.
   Запуск другой копии установки создаёт другой набор журналов.

При занятом порте используйте `artel.py down`, если этот дашборд был запущен через `up`,
либо остановите его прежним способом. Для другого порта: `python3 artel.py up --port 8766`.
Не завершайте неизвестный процесс только потому, что он занял порт.

## Повреждённый JSON или ошибка обновления

Остановите затронутый процесс, сохраните копию повреждённого файла и восстановите его
из подходящей резервной копии. Повреждённое состояние не следует заменять пустым JSON:
можно потерять исключения задач, отправленные ответы или знания. Updater сохраняет данные
и умеет откатывать код; [порядок восстановления](../UPDATE.md#ошибки-и-восстановление).
