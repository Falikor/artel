## Замечания в Bitbucket PR в простое

Артель может возвращаться к PR своих сданных задач: читать замечания людей, исправлять обоснованные
и отвечать аргументированным возражением на неподтверждённые. Поддерживается **Bitbucket Server / Data Center**,
не Bitbucket Cloud. Сетью управляет Python: REST для поиска PR, обсуждений и ответов, Git для публикации.
Для вызовов PR-обработчика список разрешённых tools включает только локальные файловые инструменты и shell, без MCP.
Работа не зависит от Jira/Bitbucket MCP в GigaCode. GigaCode получает текст задачи через существующий
Jira REST-клиент, текст обсуждения и временную копию кода.

Включение в конфиге демона:

```json
{
  "bitbucket": {
    "enabled": true,
    "url": "https://bitbucket.example.com",
    "project": "HR",
    "repo": "backend",
    "bot_user": "artel-bot",
    "batch_comments": true,
    "poll_interval_seconds": 600,
    "max_per_cycle": 1,
    "test_commands": [
      [
        "./mvnw",
        "-B",
        "test"
      ]
    ]
  }
}
```

В `tmp/.env` задайте `BITBUCKET_TOKEN=…` либо `<JIRA_PROJECT>_BITBUCKET_TOKEN=…`.
Нужен технический пользователь с правами читать PR и писать комментарии; `bot_user` — его точное
логин-имя (`name`/`slug`), а не отображаемое имя. Git-доступ на push настраивается отдельно в рабочем клоне.
`url` — корневой HTTPS-адрес, включая context path, если он есть. По умолчанию
Bitbucket работает как существующий Jira REST-клиент: HTTPS без проверки сертификата и имени хоста,
указывать файл сертификата не нужно. Это шифрует соединение, но не удостоверяет подлинность сервера.
Для проверки по системным CA задайте `verify_ssl: true`; для своего центра — `ca_file`.
Если `ca_file` уже задан, проверка по умолчанию остаётся включённой. Явное `verify_ssl: false`
отключает проверку и игнорирует `ca_file`. Redirect на страницу входа не принимается.
Эти настройки относятся к REST Bitbucket; Git fetch/push используют настройки Git/SSH.
После заполнения выполните `python3 jira_to_gigacode.py config/hrppa.json --check` и перезапустите демона.

**Как отбираются PR.** Только открытые PR для точной исходной ветки из `*-delivered.jsonl`,
в пределах настроенного репозитория и сервиса. Ветка должна содержать коммит, который демон сдал.
Адреса fetch и push у `origin` должны соответствовать одному из clone URL репозитория в Bitbucket.
PR из fork, закрытые PR и задачи без записи о сдаче автоматически не обрабатываются.
Проверка выполняется, когда обычный поиск Jira не нашёл задач на реализацию, перед остальными фоновыми работами.
Задачи, ожидающие зависимости или решения владельца, не должны мешать фоновым проверкам; причину ожидания смотрите в панели демона.

**Решение по замечаниям.** По умолчанию `batch_comments: true`: агент получает все новые
открытые замечания выбранного PR за один проход, включая вложенные реплики, и анализирует их вместе
с полным контекстом обсуждений. Для каждого ID он выбирает исправление, возражение или передачу владельцу.
Все обоснованные исправления выполняются одним вызовом исполнителя, с общими тестами,
независимым ревью и одним коммитом/push. Затем Python отправляет **отдельный ответ на каждый
обработанный комментарий** с конкретным результатом, а не общий отчёт на весь PR.
Ссылки и цитаты сверяет Python. Возражения проверяются независимым вызовом модели, а при наличии
общего исправления — дополнительно на итоговом коде. По умолчанию `max_per_cycle: 1` означает
один PR со всеми замечаниями, а не одно замечание. Для прежнего режима по обсуждениям задайте
`batch_comments: false`; тогда лимит снова считается по обсуждениям.
Неоднозначные требования и неподтверждённые возражения сохраняются в журнале и публикуются
в связанной задаче Jira для решения владельца: причина, ссылка на обсуждение и точная команда.
Собственные ответы и закрытые обсуждения пропускаются. Новая реплика человека или изменение его текста
позволяет пересмотреть решение. Учёт не сбрасывается при обычном перезапуске.
Уже обработанные до обновления обсуждения не обрабатываются повторно без новой реплики.
Большой пакет не обрезается молча: лимит контекста — 240 000 символов JSON на PR и прежние
24 000 символов JSON на обсуждение. При превышении обработка откладывается с причиной в журнале.

**Исправления.** Исполнитель работает во временной detached-копии актуальной ветки PR. Python выполняет
тестовые команды, создаёт коммит из проверенных изменений, запускает отдельную проверку diff и делает
обычный push в исходную ветку без `--force`. При отсутствии тестовых команд автоматического push не будет.
Файлы, которые появились только во время тестов, в коммит не входят. Если ветка, целевая ревизия или
обсуждение изменились во время обработки, публикация откладывается. Отметка «исправлено» отправляется
только после проверки, что новый коммит появился в PR. Демон не закрывает обсуждения, не сливает PR,
не запускает Jenkins и не переводит задачу Jira повторно. Серверные CI-хуки на push работают по правилам Bitbucket.

**Сбои и управление.** Исключения, паузы и необходимость решения владельца из управления ретраями задачи
учитываются также здесь и повторно проверяются перед публикацией. После технической ошибки предусмотрена
пауза в один час. Журнал хранит подготовленный коммит до push, поэтому сбой после публикации не требует
генерировать его заново. Ответ содержит служебную метку для восстановления учёта. Если POST завершился
неопределённо, демон ищет метку в обсуждении, но не повторяет отправку вслепую. Состояние `sending`
без найденного ответа требует проверки владельца.
Такой запрос также появляется в Jira; у него тот же ID записи, что в CLI.
При сбое одного ответа остальные подготовленные ответы пакета продолжают отправляться.
Незавершённый пакет сначала сверяется с сервером; новый коммит для него не генерируется.
Пока остались неопределённые отправки, следующий пакет этого PR ждёт решения владельца.

```bash
python3 artel.py pr list hrppa
python3 artel.py pr retry hrppa ID
python3 artel.py pr skip hrppa ID
```

`ID` — полный идентификатор из `list`. Команды меняют только локальное состояние.
`retry` разрешает повторную оценку спорного замечания, а для `prepared`/`sending` сохраняет подготовленный
результат и сначала сверяет его с сервером. Перед повтором `sending` проверьте, не появился ли ответ.
`skip` завершает обработку данной версии обсуждения без отправки сообщения. Если после подготовки
изменился конфиг или ветка, разберите сохранённый коммит и ошибку перед следующим действием.
В дашборде виден этап ревью/доработки и лог; отдельного списка PR в интерфейсе пока нет.

Уведомления о замечаниях одного PR объединяются в собственный комментарий Jira и обновляются
при изменении состояния. Они учитывают `jira.enabled` и `jira.result_comments`;
если Jira выключена, журнал и CLI остаются доступны. Очередь доставки хранится в
`logs/{инстанс}-notifications.json`. Текст в Jira сам по себе не подтверждает повторную отправку.

[Все настройки этого механизма](CONFIGURATION.md).

У каждого элемента `services[]` можно задать свой раздел `bitbucket`, который сливается с общим.
ENV главнее обоих уровней: общий `BITBUCKET_REPO` перекроет репозитории всех сервисов.
Состояние хранится в `logs/<инстанс>-pr-review-<идентификатор>.json`, рядом файл блокировки.
Завершённые и спорные записи сокращаются при превышении 1000 записей, неразобранные публикации сохраняются.
Подготовленные коммиты удерживаются ссылками `refs/artel-pr-review/*` в репозитории.
Обновляющий скрипт сохраняет журнал вместе с остальными логами.

Временная Git-копия изолирует рабочие файлы, но не права процесса. Ограничения prompt не являются
песочницей. Второй вызов модели также может ошибиться: проверяемые цитаты и тесты уменьшают риск,
но не доказывают истинность любого возражения. Реальное подключение к вашей корпоративной версии
Bitbucket необходимо проверить после настройки на минике.

[справочник Pull Requests API](https://developer.atlassian.com/server/bitbucket/rest/v1000/api-group-pull-requests/).
