# Поведение и промпты демонов

**Русский** · [English](PROMPTS.en.md)

[Главная](../README.ru.md) · [Конфигурация](CONFIGURATION.md) · [Дашборд](DASHBOARD.md)

Вкладка **Промпты** задаёт индивидуальную роль, общие инструкции, инструкции отдельных
этапов и имя субагента-исполнителя. Настройки относятся к выбранному демону и всем его
сервисам. Другие демоны продолжают работать со своими настройками.

## Настройка через дашборд

1. Откройте **Промпты** и выберите демона. В списке есть и настроенные, но ещё не запущенные демоны.
2. Выберите профиль: **Разработчик**, **Тестировщик** или **Своя роль**.
3. При необходимости измените имя установленного субагента и общие инструкции.
4. Выберите этап и добавьте относящиеся только к нему указания. Переключение этапа сохраняет черновик.
5. Нажмите **Предпросмотр инструкций**, проверьте текст и затем **Сохранить**.

Предпросмотр показывает настраиваемую часть запроса. Он не запускает GigaCode и не
изменяет настройки. Постановка задачи, контекст репозитория и обязательные правила
добавляются Артелью при настоящем запуске.

**Из конфига** подготавливает возврат к разделу `prompts` JSON-конфига; нажмите
**Сохранить**, чтобы применить его. Если раздела нет, вернётся стандартный разработчик
с субагентом `jira-to-deploy-orchestrator`. **Отменить правки** убирает только несохранённый
черновик. При смене демона и переходе между вкладками черновики сохраняются в текущей
странице браузера; перезагрузка их не сохраняет. Конфликт изменений из двух вкладок
не перезаписывает данные молча: редактор предлагает сверить серверную версию, сохраняя черновик.

## Профили и этапы

| Профиль | Поведение |
|---|---|
| `developer` — Разработчик | Стандартный процесс Артели; дополнительных инструкций профиля нет |
| `testing` — Тестировщик | Составляет проверяемые сценарии из критериев приёмки, изучает тестовый стек, добавляет и запускает автоматические тесты на основное поведение, границы и регрессии |
| `custom` — Своя роль | Специализация задаётся общими инструкциями и указаниями этапов |

Тестировщик не должен ослаблять проверки ради успешного результата. Продуктовый код он
меняет, если это входит в постановку; иначе описывает воспроизводимый дефект. В отчёте
нужны фактические проверки и их результаты. Если обязательный сценарий нельзя проверить
без дополнительных данных или окружения, используется существующий протокол `BLOCKED`.
Профиль не меняет JQL и не создаёт отдельную очередь тестирования: выбор задач по-прежнему
определяется конфигом Jira и маршрутизацией сервисов.

| Ключ этапа | Куда добавляются инструкции |
|---|---|
| `generation` | Основное выполнение задачи и ручная переделка по новой постановке |
| `review` | Независимое ревью кода |
| `rework` | Исправление замечаний независимого ревьюера |
| `explore` | Исследование бэклога в простое |
| `pr_review` | Разбор замечаний Bitbucket, исправления и ответы |
| `retro` | Ретроспектива сданных задач и извлечение уроков |
| `memory` | Проверка кандидатов памяти по коду и тестам |

Для каждого запроса сначала собираются инструкции профиля, общие указания и текст
выбранного этапа. Затем добавляется стандартный запрос Артели. Пустое поле не отменяет
этап и не убирает его штатные инструкции. Пользовательский текст не заменяет правила
веток, доступов, проверок, публикации и маркеров `SUCCESS` / `BLOCKED`.

## Промпт и команда терминала

Редактор хранит **текст для модели**, передаваемый существующему GigaCode CLI через stdin.
Это не редактор shell-скриптов: добавленные строки не исполняются напрямую оболочкой.
Путь к CLI, реальные команды тестов, расписания и включение функций остаются отдельными
[настройками](CONFIGURATION.md).

Поле **Субагент-исполнитель** содержит имя без `/`, например `jira-to-deploy-orchestrator`.
Оно используется при выполнении задачи и доработке после ревью. Указанный субагент должен
быть заранее установлен в GigaCode для пользователя, запускающего демона; переименование
в форме само по себе файл субагента не создаёт. См. [установку исполнителя](../subagents/README.md).
Собственный субагент должен поддерживать обязательный протокол завершения Артели.

## Пример JSON-конфига

Фрагмент добавляется на верхний уровень конфига выбранного демона:

```json
{
  "prompts": {
    "profile": "testing",
    "subagent": "jira-to-deploy-orchestrator",
    "instructions": "В отчёте отделяй подтверждённые дефекты от непроверенных предположений.",
    "stages": {
      "generation": "Добавляй регрессионный тест для каждого воспроизведённого дефекта.",
      "review": "Проверь негативные сценарии и обработку ошибок интеграций.",
      "explore": "Ищи непроверяемые критерии приёмки и отсутствующие тестовые данные."
    }
  }
}
```

Все поля необязательны; пропущенные этапы получают пустой текст. У общих инструкций
и каждого этапа отдельный лимит **6000 символов**. ENV-эквивалентов и отдельных
`services[].prompts` нет. Неизвестные поля, роли и этапы отклоняются.

## Когда настройки применяются

Сохранённые настройки UI главнее раздела `prompts` в конфиге. Они записываются атомарно в
`logs/{instance}-prompts.json`, переживают перезапуск и штатное обновление. Изменение JSON-конфига
требует перезапуска демона; сохранение через UI его не требует.

Текущая задача или фоновая операция заканчивается с теми инструкциями, с которыми началась.
Новые инструкции применяются перед следующей работой. Вкладка показывает, применены ли
настройки, ожидают окончания работы или следующего запуска демона.

Изменение поведения учитывается в проверке контекста повторов. Ранее начатая задача
не должна автоматически продолжаться с новым профилем: для такого повтора требуется
подтверждение. Само сохранение инструкций не снимает исключение задачи, паузу или `BLOCKED`.

В демо можно менять черновик и смотреть предпросмотр; сохранение отключено. Режим
`--no-control` и просмотр чужого каталога логов также не позволяют менять настройки.
Повреждённый файл промптов останавливает получение новой работы, вместо незаметного
возврата к стандартному поведению.
