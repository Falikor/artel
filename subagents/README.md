# Исполнитель задач Артели для GigaCode CLI

Готовое определение: [jira-to-deploy-orchestrator.md](jira-to-deploy-orchestrator.md).
Формат — Markdown с YAML frontmatter, имя соответствует вызовам из Артели.

## Установка на минике

1. Сохраните резервную копию существующего `jira-to-deploy-orchestrator.md`, если он уже установлен.
2. Поместите новый файл в `~/.gigacode/agents/jira-to-deploy-orchestrator.md` **под пользователем, запускающим демонов**. Это общий исполнитель для его репозиториев. Альтернатива — `.gigacode/agents/` в каждом рабочем репозитории сервиса; проектный вариант имеет приоритет над пользовательским, поэтому проверьте, что старый проектный файл не перекрывает новый.
3. В каждом рабочем репозитории проверьте установленную версию OpenSpec, инициализацию проекта и доступность workflow propose, apply, sync, archive. Сам агент не устанавливает инструменты автоматически. Используйте инструкции вашей версии OpenSpec; slash-команды не запускаются в shell.
4. Откройте GigaCode CLI в рабочем репозитории и проверьте агента через `/agents manage`. Выполните пробную задачу на тестовом репозитории с локальным origin, не в рабочем проекте.
5. Для строгого протокола задайте в конфиге демона `"general": {"require_success_marker": true}` (добавьте ключ в существующий раздел). Перезапустите демонов после обновления Артели и определения агента.

`update_artel.py` доставляет каталог `subagents/` в установку Артели. Он **не перезаписывает** определения в домашней папке и рабочих репозиториях: туда файл нужно установить отдельно. В текущей разработке не проверялись реальные GigaCode CLI и корпоративные проекты на минике.

## Что делает агент

Читает переданную задачу и проверяет рабочую ветку → создаёт или продолжает OpenSpec change → реализует → выполняет применимые проверки → синхронизирует спецификации → архивирует завершённый change → возвращает отчёт и текстовый финальный сигнал.

Команды ассистента обычно имеют вид `/opsx:propose`, `/opsx:apply`, `/opsx:sync`, `/opsx:archive`. Конкретное имя зависит от интеграции OpenSpec. Если механизм slash-команд недоступен внутри субагента, он читает установленную инструкцию соответствующего workflow и выполняет её шаги. Если нет и инструкции, возвращает блокировку. Автономное выполнение не отменяет явно обязательные согласования из правил проекта.

Push, независимое ревью, деплой и перевод Jira остаются ответственностью демона. Агент не получает MCP-инструменты через allowlist; shell разрешён для Git, OpenSpec, сборки и тестов. Ограничения текста **не заменяют** ОС-права, изоляцию процесса и ограничения сети.

## Протокол результата

Последняя непустая строка окончательного ответа родителя:

- `CODE_GENERATION_SUCCESS` — реализация, проверки и применимый OpenSpec-цикл завершены;
- `CODE_GENERATION_BLOCKED` — нужен доступ, инструмент, уточнение или другое внешнее действие;
- `CODE_GENERATION_FAILED` — выполнение не удалось.

Это строки результата, а не команды терминала. Блок LESSONS выводится перед ними и только по запросу. Родитель должен передать итог субагента в собственный окончательный ответ.

Для BLOCKED перед финальным сигналом выведите вопрос владельцу между отдельными строками
`BLOCKED_QUESTION_START` и `BLOCKED_QUESTION_END`. Укажите недостающий факт или действие,
которое позволит продолжить. Родитель должен сохранить этот блок в своём финальном ответе.
Не включайте секреты, полный журнал инструментов и неподтверждённые утверждения.

Ненулевой код выхода CLI и явный отдельнострочный сигнал BLOCKED/FAILED запрещают продолжение независимо от частично написанного кода. Для успеха проверяется отдельная последняя непустая строка. В режиме совместимости (`require_success_marker: false`) код 0 без сигнала по-прежнему может быть принят при наличии работы; для этого исполнителя рекомендуется строгий режим. Те же правила применяются при доработке после ревью.

Маркер — утверждение модели, а не доказательство выполнения OpenSpec: Python не валидирует
полноту архива и истинность тестового отчёта. Сохраняйте независимое ревью.
FAILED остаётся технической неудачей. BLOCKED — отдельное ожидание: демон публикует вопрос
в Jira, пытается вернуть задачу в настроенный статус бэклога и ждёт изменения постановки
или обсуждения человека вместо автоматического ретрая. [Подробный порядок](../docs/WORKFLOW.md#blocked-ожидание-уточнения).

## Проверка перед рабочим запуском

На тестовом репозитории проверьте четыре сценария: успешная задача с архивом и финальным сигналом; отсутствующий OpenSpec; падающая обязательная проверка; доработка уже архивированного change после ревью. В последних двух случаях не должно быть ложного успеха или переписывания прежнего архива. Убедитесь, что агент не пушит и не вызывает Jenkins/Jira. Проверьте имена доступных tools в установленной версии CLI, если она отклоняет allowlist.

Основания формата и workflow: [субагенты GigaCode CLI](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/subagents), [официальный OpenSpec OPSX](https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md).
